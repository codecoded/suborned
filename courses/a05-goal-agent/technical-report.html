How the loop works

  1. Select the highest semantic-version agent/human GDD pair and compare both hashes against registered local main checkouts. Current v0.24.0 matches main. A read-only remote-main check matched af46f14dfd6edd29eeed6123e38778081275abef.
  2. Bootstrap/reuse a corpus-hash-specific SurrealDB index. Pin every retrieval call to that corpus. Extract literal GDD quotes, acceptance criteria, dependencies, scoring reasons and a disposition for every numbered section.
  3. Inspect production, test and headless-consumer paths through bounded reads/searches. The model receives compact navigation; exact hashes stay archived. A search miss alone cannot establish a gap.
  4. Generate acceptance tests and independently review them. Rejected proposals receive concrete feedback within the iteration/call limits; interrupted revisions retain earlier faults. Only an approved, compile-clean assertion-failure baseline permits production writing. Tests then freeze.
  5. A separate writer returns structured exact-match patches to the declared production files. The coordinator applies them, runs acceptance and full regression checks, rescans source hashes, asks for independent review, and reassesses the GDD requirement. Repairs stay bounded; exhaustion remains INCOMPLETE.
  6. Persist the backlog under the goal hash. On rerun, compare GDD and inspected-file hashes and rerun each retained selector with its minimum test count. Valid completed work is skipped. Changed code/design invalidates proof. COMPLETE requires every discovered requirement in the scope to be supported.
